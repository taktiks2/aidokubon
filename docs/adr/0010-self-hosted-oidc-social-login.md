# 認証は外部の認証サービスを使わず、OIDC のソーシャルログインを自前で組む

家族はパスワードを覚えられず、一般公開したあとは退会とデータの削除（ADR-0002）に確実に応える必要がある。ユーザーの情報を自前の DB だけで完結させるため、`openidconnect` クレートで Google ログインを自前でつなぐ。LINE ログインも OIDC に対応しているので、あとから同じ仕組みで足す。パスワードは持たない。セッションは JWT にせず、推測できない ID を HttpOnly の Cookie に入れ、中身を PostgreSQL に保存する。ログアウトやメンバーを外したときに、その場で無効にできるようにするため。

## Considered Options

| 案 | 見送った理由 |
|---|---|
| 外部の認証サービス（Clerk、Auth0、Supabase Auth、Firebase Auth） | 実装は最も少ないが、ユーザーの情報が 2 か所に分かれ、webhook での同期と、退会の処理が 2 か所で必要になる。規模が大きくなると課金される |
| メールのマジックリンク | メールの送信基盤と、到達率への対策が必要になる |
| ID とパスワード | 家族が忘れる。再設定の仕組みと、漏洩したときの責任が重い |

## Consequences

- state、nonce、PKCE の処理は `openidconnect` クレートに、セッションの管理は tower-sessions のような実績のあるライブラリに任せ、自前の実装を減らす。
- スマホのアプリに展開するときのために、同じセッションの ID を `Authorization: Bearer` でも受け取れるようにしておく（ADR-0013）。
